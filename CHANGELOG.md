# Changelog

All notable changes to this project are documented here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this
project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Entries above `0.1.0` are generated by
[release-please](https://github.com/googleapis/release-please) from Conventional Commit
subjects, then **edited by hand in the release PR before it is merged**. That editing step
is not optional housekeeping: a generated subject like `fix(vault): split colliding leads`
does not tell you your `sluice.yaml` now means something different, and per the section
below that is the change class that matters most here. Add the migration note to the
release PR; merging it is what tags the release.

## What counts as breaking here

**A breaking CONFIG change outranks a breaking API change**, and this file is written on
that assumption. Nothing imports `sluice` as a library; what people have invested in is
their `sluice.yaml` and their vault. So the entries that matter most are the ones that
change what an existing config *means* — and the worst of those are silent, because a
config that still parses and still runs simply starts doing something else.

Any change in the following classes is `Changed` at minimum and gets an explicit
migration note, even when no key is renamed:

- **What an unset or empty value means.** Every preference gate abstains when
  unconfigured (see `0.1.0` below). A change that made an empty list mean "match nothing"
  instead of "match everything" would silently bin an entire job hunt while looking like
  a no-op — this has happened once, which is why the behaviour is now pinned by a test.
- **What a default value is**, where the default is load-bearing rather than cosmetic.
- **Where a file is read from or written to**, including the vault layout and any
  XDG-resolved path.
- **What a status transition is permitted to do**, since statuses are the record of what
  you have actually applied to.

## [0.1.0] - 2026-08-06

The baseline, and the only hand-written section: it is the seed release-please starts
from, so everything after it is generated and then edited. It is deliberately NOT a cut
release — no `v0.1.0` tag exists, and adopting release-please does not create one. The
first tag will be whatever the first release PR proposes. What follows is the
shipped surface as of this baseline rather than a diff against a predecessor — there was no
previous release to differ from.

### The pipeline

`ingest -> triage -> cv -> apply -> track`, each a sub-app under a shared core, driven by
one YAML file and the environment.

- **`sluice init`** — an onboarding wizard that writes a config from a question catalogue
  and scaffolds a Judging Profile in your vault. Every question you skip is written
  **commented out**, so an unanswered run produces a config that behaves exactly like no
  config at all. It never overwrites an existing file, so re-running is safe.
- **`sluice ingest`** — scrapes configured job boards through a browser fetcher into a
  lead store, de-duplicating against what it has already seen. Sources are declarative
  plugins; one broken source is logged and skipped rather than sinking the run.
- **`sluice triage`** — deterministic classification plus an optional LLM judge that reads
  its criteria from *your* vault (`Job Applications/Judging Profile.md`). There IS a
  fallback compiled in, and it is not a hidden set of preferences: it states only that
  nothing is configured and declines to invent an opinion. `--no-llm` runs the
  deterministic half alone.
- **`sluice cv`** — composes a CV tailored to a shortlisted lead from a closed bundle of
  your verified experience entries, then gates it. See *Fabrication gate* below.
- **`sluice apply`** — stages the rendered CV and a prep packet for a shortlisted lead.
- **`sluice track`** — reconciles the funnel from email and calendar signals, and can
  advance a lead to `applied` from a confirmation receipt when the evidence is strong
  enough (and proposes it for a human otherwise).
- **`sluice leads`** — maintenance passes: `dedupe`, `expire`, `reconcile`. These
  **report and change nothing** until told otherwise; the pipeline commands write by
  default. None of them offers `--dry-run`, because the default *is* the dry run.
- **`sluice doctor`** — preflights every configured backend. `--offline` classifies from
  config alone without a round trip.
- **`sluice --version`** — prints the version, for bug reports.

### Guarantees this release makes

These are enforced by tests rather than promised in prose.

- **No shipped preferences.** Every preference gate — title, location, company, the coarse
  ingest relevance gate, pay floors — defaults to empty or zero, and an unconfigured gate
  **abstains**, passing every lead through. Sluice holds no opinion about which jobs are
  good.
- **No personal data in the package.** No employer names, locations, contact details or
  hostnames ship in `sluice/`. Your values live in your config and your vault.
- **Never-clobber.** A re-scrape of a lead you already have touches only its `last_seen`
  marker — never its status, your edits, or the note body. Field updates are surgical: the
  edit is re-derived from the *fresh* note and committed atomically, so another writer's
  other keys and your body survive, and a sustained race refuses loudly rather than
  overwriting. This is best-effort, **not a lock**: a residual window remains between the
  freshness check and the replacement, and the likeliest other writer is you, in Obsidian,
  holding no lock at all.
- **Never-regress.** Status only moves forward, and triage may never touch a lead that has
  entered the application lifecycle. A lead you have applied to cannot be quietly reset.
- **Non-resurrection, bounded.** A duplicate you merged away is not re-created by a later
  scrape *through the identity the store recorded when you merged it* — for the vault, the
  note name it was seated at. A re-scrape whose title has drifted past every name candidate
  falls outside that and is created afresh: a visible duplicate, which is the direction to
  fail in. The absolute form is not something a store can deliver, and claiming it would
  hide the residual rather than bound it.
- **Fabrication gate.** Every bullet under `WORK EXPERIENCE` must cite a real entry from
  your verified bundle, and every number in such a bullet must appear in the entry it
  cites. The PROFILE prose carries no per-bullet citations and is held to a bundle-wide
  numeric floor instead; `CERTIFICATES` and `EDUCATION` are not citation-checked. A CV that
  fails is never rendered — composition retries once, then the lead is skipped. The
  qualitative gap that leaves is exactly what the layer above it is for: an advisory LLM
  audit flags unsupported claims and withholds the send-ready pointer until you sign off
  (`cv.require_signoff`, on by default; `sluice cv signoff` releases a held lead).

### Requirements and known limitations

- **Python 3.12+.** `sluice/` is standard-library only apart from `pyyaml`; the Google and
  WeasyPrint integrations are opt-in extras.
- **Rendering needs setting up before `sluice cv run` can produce a PDF.** The default
  `cv.renderer` is `script`, which shells out to an external render script that this
  repository does not ship — so on a fresh install it fails at construction with a message
  telling you so. Either point `cv.render_script` at your own script, or install the
  bundled renderer with `pip install 'sluice[render]'` and set `cv.renderer: weasyprint`.
- **Ingest needs a running browser server**, and so does `cv` whenever a lead's dossier is
  not already cached — the fetcher is opened lazily on a cache miss. The LLM backends speak
  HTTP, and `track` and a non-`--offline` `doctor` reach the network too. The genuinely
  offline commands are `triage --no-llm`, `leads`, `init`, and `doctor --offline`.
- **The LLM backends need credentials** unless you use the flat-rate CLI backend. Run
  `sluice doctor` to see what is reachable before a real run.
